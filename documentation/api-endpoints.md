# REST API Jobly

**Статус:** Draft V1 — согласуется с [моделью данных](База%20данных.md)
**Дата актуализации:** 13.11.2026
**Base URL:** `/api/v1`
**Формат:** JSON, UTF-8
**Клиент:** React SPA
**Бэкенд:** стек не выбран — контракт от него не зависит (см. раздел 1)

---

## 1. Принципы контракта

Бэкенд пока в раздумьях, поэтому контракт написан так, чтобы его можно было
реализовать на любом стеке (Node, Python, C#, Kotlin, Go) и не переписывать
фронтенд при смене выбора.

1. **Контракт первичен.** Источник правды — `openapi.yaml`, а не код. Из него
   на фронте генерируются TypeScript-типы и клиент (`openapi-typescript`,
   Orval или аналог), на бэкенде — заготовки контроллеров или валидация.
   Этот документ — человекочитаемая версия.
2. **Никакой привязки к фреймворку.** Нет ничего, что зависит от конкретной
   библиотеки сессий, сериализации или ORM: только HTTP, JSON и стандартные
   заголовки.
3. **Бэкенд считает всё сам.** Оценка теста, версия документа, статус
   вакансии, итоговый `score` — только на сервере. Клиент ничего из этого не
   присылает.
4. **Модель — медленная.** Генерация идёт через локальную YandexGPT 5 Lite и
   может занимать десятки секунд. Любая операция с моделью **асинхронная**
   (раздел 2.7), фронтенд не должен висеть на одном HTTP-запросе.

### Контуры

| Контур | Префикс | Кто обращается | Аутентификация |
|---|---|---|---|
| User | `/api/v1/**` | пользователь через React-приложение | cookie-сессия + CSRF |
| Admin | `/api/v1/admin/**` | администратор: источники, парсинг, база знаний целиком | та же сессия + роль `ADMIN` |

Парсер собирает вакансии **внутри бэкенда** (планировщик, воркер) и API для
записи вакансий снаружи не имеет. Если парсер станет отдельным сервисом,
понадобится третий, machine-to-machine контур — см. раздел 14.

## 2. Сквозные соглашения

### 2.1 Аутентификация

Session ID передаётся только cookie: `HttpOnly`, `Secure`, `SameSite=Lax`. В
`localStorage` и `sessionStorage` ничего секретного не хранится.

Выбор сессии, а не JWT в заголовке, сделан сознательно: не нужно хранить токен
в JS-доступном месте, а отзыв сессии при смене пароля или блокировке
мгновенный. Реализуется на любом бэкенде.

CSRF-защита включена. Токен выдаётся `GET /auth/csrf` и передаётся в
`X-CSRF-Token` во всех изменяющих запросах (`POST`, `PUT`, `PATCH`,
`DELETE`). `GET` состояние не меняет.

Фронтенд и API должны жить на одном сайте (один домен или поддомены), иначе
`SameSite=Lax` не сработает. В разработке это решается proxy в dev-сервере
React.

### 2.2 Заголовки

| Заголовок | Где | Назначение |
|---|---|---|
| `X-CSRF-Token` | все изменяющие запросы | защита от CSRF |
| `Idempotency-Key` | запуск генерации, создание тестов и записей через нейросеть | UUID; повтор возвращает уже созданную операцию |
| `X-Correlation-Id` | опционально | связывает запрос с логами |
| `Accept-Language` | опционально | язык сообщений об ошибках |

### 2.3 Именование и типы

- JSON: `camelCase`; идентификаторы — UUID строкой.
- Даты и время — ISO 8601 в UTC: `2026-11-12T10:15:00Z`.
- Перечисления — `UPPER_SNAKE_CASE`: `JOB`, `INTERNSHIP`, `COVER_LETTER`.
- Отсутствие значения — `null`, а не пустая строка и не пропуск поля.
- Деньги — число и отдельное поле `currency` (`RUB`, `USD`).

### 2.3.1 Соответствие модели данных и API

Физическая схема и правила хранения описаны в [модели данных](База%20данных.md).
API — публичная проекция этой схемы: имена столбцов БД в `snake_case` выдаются
в JSON в `camelCase`; внутренние значения перечислений в нижнем регистре
преобразуются в публичные значения `UPPER_SNAKE_CASE`.

| Внутреннее поле | Публичное представление |
|---|---|
| `user_roles` | массив строк `roles` в `/auth/me` и `/users/me` |
| `user_resumes.parse_llm_request_id` | `parseOperationId`; `parseStatus` берётся из статуса связанного запроса, включая `CANCELLED` |
| `generated_documents.id` | стабильный `documentId`; поля версии читаются из `generated_document_versions` |
| `llm_requests.status` | ресурс операции; `resultRef` и `queuePosition` вычисляются API |
| `test_attempts.grading_llm_request_id` | `operationId` при статусе `CHECKING` |

| Внутреннее значение БД | Значение API |
|---|---|
| `vacancies.kind`: `job`, `internship` | `JOB`, `INTERNSHIP` |
| `vacancies.status`: `active`, `archived` | `ACTIVE`, `ARCHIVED` |
| `parsing_runs.status`: `running`, `success`, `failed` | `RUNNING`, `SUCCESS`, `FAILED` |
| `knowledge_items.kind`: `question`, `task` | `QUESTION`, `TASK` |
| `difficulty`: `junior`, `middle`, `senior` | `JUNIOR`, `MIDDLE`, `SENIOR` |
| `generated_documents.kind`: `resume`, `cover_letter` | `RESUME`, `COVER_LETTER` |
| `origin`: `manual`, `ai` | `MANUAL`, `AI` |
| `user_roles.role`: `user`, `admin` | `USER`, `ADMIN` |
| `llm_requests.purpose`: `resume_parse`, `resume`, `cover_letter`, `knowledge_item`, `test`, `attempt_check` | `RESUME_PARSE`, `RESUME`, `COVER_LETTER`, `KNOWLEDGE_ITEM`, `TEST`, `ATTEMPT_CHECK` |
| `llm_requests.status`: `pending`, `done`, `failed`, `cancelled` | `PENDING`, `DONE`, `FAILED`, `CANCELLED` |
| `knowledge_items.status`, `tests.status`: `active`, `archived` | `ACTIVE`, `ARCHIVED` |
| `test_attempts.status`: `in_progress`, `checking`, `completed` | `IN_PROGRESS`, `CHECKING`, `COMPLETED` |

`PENDING` означает, что операция либо ждёт в очереди, либо выполняется.
Идентификатор операции — это `llm_requests.id`; отдельная запись `operations`
в БД не нужна.

### 2.4 Ошибки

Формат — RFC 9457 `application/problem+json`:

```json
{
  "type": "https://jobly.example/errors/validation-failed",
  "title": "Ошибка валидации",
  "status": 422,
  "detail": "Поле title не может быть пустым",
  "instance": "/api/v1/knowledge-items",
  "correlationId": "018f...",
  "errors": [
    { "field": "title", "code": "REQUIRED", "message": "Обязательное поле" }
  ]
}
```

Для форм на фронте используется массив `errors` — по `field` ошибка
привязывается к полю. Stack trace, SQL и содержимое промптов в тело ошибок не
попадают.

| Код | Когда |
|---|---|
| `400` | синтаксически неверный запрос |
| `401` | нет сессии или она истекла |
| `403` | нет прав на действие |
| `404` | объекта нет **или** он чужой — существование не раскрываем |
| `409` | конфликт: занятый email, повторная отправка теста |
| `413` | файл резюме слишком большой |
| `415` | неподдерживаемый формат файла |
| `422` | доменная валидация не пройдена |
| `429` | превышен лимит запросов |
| `503` | модель недоступна или перегружена |

### 2.5 Списки и пагинация

Курсор-based: `?limit=20&cursor=<opaque>`. Ответ:

```json
{ "items": [], "nextCursor": "018f...", "hasMore": true }
```

Offset не используется: парсер добавляет вакансии постоянно, и страницы
съезжали бы. `limit` по умолчанию 20, максимум 100.

### 2.6 Сортировка и фильтры

`?sort=-publishedAt` (минус — по убыванию). Допустимые поля сортировки и
фильтров описаны у каждого списка. Неизвестный параметр — `400`, а не тихое
игнорирование.

### 2.7 Асинхронные операции

Всё, что обращается к модели, возвращает `202 Accepted` и ресурс
**операции**. Операция — это `llm_requests` из модели данных, показанный
клиенту.

```json
{
  "id": "018f...",
  "purpose": "COVER_LETTER",
  "status": "PENDING",
  "createdAt": "2026-11-12T10:15:00Z",
  "resultRef": null,
  "error": null
}
```

| `status` | Смысл |
|---|---|
| `PENDING` | принята, ждёт очереди или выполняется |
| `DONE` | готово, `resultRef` указывает на результат |
| `FAILED` | не удалось, причина в `error` |
| `CANCELLED` | отменена пользователем |

`resultRef` — ссылка на созданный ресурс:

```json
{ "type": "GENERATED_DOCUMENT", "id": "018f...", "href": "/api/v1/documents/018f..." }
```

Как узнавать о результате:

1. **Polling (по умолчанию):** `GET /operations/{id}` раз в 2–3 секунды.
   Работает везде и проще всего реализуется на любом бэкенде.
2. **SSE (необязательно):** `GET /operations/{id}/events` отдаёт события
   `status`, закрывается на `DONE`/`FAILED`/`CANCELLED`. Если бэкенд его не поддерживает,
   фронтенд обходится polling.

`POST /operations/{id}/cancel` отменяет только ещё не завершённую операцию;
для уже выполняющейся операции сервер может вернуть `409`.

Локальная модель обрабатывает ограниченное число запросов одновременно, поэтому
в ответ добавляется `queuePosition` (если известна). Лимит на пользователя —
не более 3 незавершённых операций; при превышении `429`.

Запрос с `Idempotency-Key` при повторе возвращает уже созданную операцию, а не
запускает вторую. Это защищает от двойного клика и от повторной отправки при
обрыве сети.

### 2.8 Права

Проверка двойная: на уровне маршрута (залогинен ли, есть ли роль) и на уровне
объекта (чей это документ). Чужие резюме, документы и попытки тестов
возвращают `404`.

## 3. Аутентификация

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `GET` | `/auth/csrf` | — | Выдаёт CSRF-токен |
| `POST` | `/auth/register` | — | Регистрация |
| `POST` | `/auth/login` | — | Вход по email и паролю. Меняет session ID |
| `POST` | `/auth/logout` | пользователь | Удаляет серверную сессию |
| `GET` | `/auth/me` | пользователь | Профиль и роли |
| `POST` | `/auth/password` | пользователь | Смена пароля, завершает остальные сессии |

Тело регистрации:

```json
{ "email": "user@example.com", "password": "...", "fullName": "Иван Иванов" }
```

При неуспешном входе ответ **одинаковый независимо от причины**: нет такого
пользователя или неверный пароль. Иначе API превращается в средство перебора
email. Вход ограничен по частоте.

`GET /auth/me` — единственный запрос, который React делает при старте
приложения, чтобы понять, залогинен ли пользователь:

```json
{
  "id": "018f...",
  "email": "user@example.com",
  "fullName": "Иван Иванов",
  "roles": ["USER"],
  "createdAt": "2026-11-12T10:00:00Z"
}
```

Пока `401` — фронтенд показывает экран входа.

## 5. Резюме пользователя

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/resumes` | Список своих резюме |
| `POST` | `/resumes` | Загрузить резюме (`multipart/form-data`) |
| `GET` | `/resumes/{resumeId}` | Резюме: метаданные, `parsedData`, навыки |
| `PATCH` | `/resumes/{resumeId}` | Изменить `title` или поправить `parsedData` |
| `PUT` | `/resumes/{resumeId}/skills` | Полностью заменить список навыков |
| `DELETE` | `/resumes/{resumeId}` | Удалить резюме |
| `GET` | `/resumes/{resumeId}/file` | Скачать исходный файл |

**Загрузка.** Поля формы: `file` (PDF или DOCX, до 10 МБ), `title`
(необязательно). Ответ — `201` с резюме. Разбор текста и навыков может занять
время, поэтому резюме создаётся сразу, а разбор идёт как операция:

```json
{
  "id": "018f...",
  "title": "Резюме Backend",
  "uploadedAt": "2026-11-12T10:15:00Z",
  "parseStatus": "PENDING",
  "parseOperationId": "018f..."
}
```

`parseStatus`: `PENDING`, `DONE`, `FAILED`, `CANCELLED`. Пока разбор не
завершён, генерация документов из этого резюме недоступна (`422`).

**Данные резюме.** После разбора `GET /resumes/{id}` возвращает:

```json
{
  "id": "018f...",
  "title": "Резюме Backend",
  "parseStatus": "DONE",
  "parsedData": {
    "contacts": { "email": "...", "phone": "...", "links": [] },
    "experience": [
      { "company": "...", "position": "...", "from": "2024-06", "to": null, "description": "..." }
    ],
    "education": [],
    "projects": []
  },
  "skills": [
    { "id": "018f...", "name": "PostgreSQL", "level": null }
  ]
}
```

Пользователь может исправить `parsedData` через `PATCH`: модель ошибается при
разборе, и генерировать из неверных данных нельзя. Правка навыков —
`PUT /resumes/{id}/skills` (полная замена списка).

`raw_text` резюме клиенту **не отдаётся** — только структурированные данные.

## 6. Вакансии

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/vacancies` | Поиск и список |
| `GET` | `/vacancies/{vacancyId}` | Карточка вакансии |
| `GET` | `/vacancies/{vacancyId}/match` | Сопоставление с резюме |
| `GET` | `/vacancies/{vacancyId}/knowledge-items` | Вопросы и задачи по навыкам вакансии |

Вакансии создаёт только парсер. Методов `POST`, `PATCH` и `DELETE` для
пользователя нет.

### Поиск

`GET /vacancies` — фильтры:

| Параметр | Смысл |
|---|---|
| `q` | полнотекстовый поиск по названию и описанию |
| `kind` | `JOB` или `INTERNSHIP` |
| `skillIds` | список навыков через запятую; вакансии, где есть **все** |
| `companyId` | работодатель |
| `sourceId` | источник |
| `location` | город |
| `remote` | `true` — только удалённые |
| `salaryFrom` | минимальная верхняя граница вилки |
| `publishedAfter` | дата публикации |

По умолчанию возвращаются только `status = ACTIVE`. Сортировка:
`-publishedAt` (по умолчанию), `-salaryTo`, `relevance` (при наличии `q`).

Элемент списка — краткая проекция, без полного описания:

```json
{
  "id": "018f...",
  "kind": "INTERNSHIP",
  "title": "Стажёр Backend",
  "company": { "id": "018f...", "name": "Acme" },
  "location": "Москва",
  "remote": true,
  "salary": { "from": 50000, "to": 80000, "currency": "RUB" },
  "skills": [{ "id": "018f...", "name": "Python", "isRequired": true }],
  "publishedAt": "2026-11-10T08:00:00Z",
  "source": { "id": "018f...", "name": "hh" }
}
```

### Карточка

`GET /vacancies/{id}` добавляет `description`, `requirements`, `url`
(ссылка на оригинал), `parsedAt`, `status`. Архивные вакансии **остаются
доступными по прямой ссылке**: на них могут ссылаться созданные документы.
В списке они не показываются.

### Сопоставление

`GET /vacancies/{id}/match?resumeId=<uuid>` — чем резюме пересекается с
вакансией. Считается без обращения к модели, по таблицам навыков.

```json
{
  "resumeId": "018f...",
  "matchedSkills": [{ "id": "018f...", "name": "Python", "isRequired": true }],
  "missingSkills": [{ "id": "018f...", "name": "Docker", "isRequired": true }],
  "extraSkills": [{ "id": "018f...", "name": "Figma" }],
  "coverage": 0.67
}
```

`coverage` — доля обязательных навыков вакансии, которые есть в резюме.

### Подготовка к вакансии

`GET /vacancies/{id}/knowledge-items` — записи базы знаний, чьи навыки
пересекаются с навыками вакансии. Фильтры и ответ — как у `/knowledge-items`
(раздел 9), плюс поле `matchedSkillIds` у каждой записи.

## 9. Документы: резюме и письма под вакансию

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/vacancies/{vacancyId}/documents` | Запустить генерацию |
| `GET` | `/documents` | Мои документы |
| `GET` | `/documents/{documentId}` | Документ |
| `GET` | `/documents/{documentId}/versions` | Все версии этого документа |
| `POST` | `/documents/{documentId}/regenerate` | Новая версия |
| `PATCH` | `/documents/{documentId}` | Ручная правка текста — новая версия |
| `GET` | `/documents/{documentId}/export` | Скачать: `?format=pdf`, `docx` или `md` |
| `DELETE` | `/documents/{documentId}` | Удалить |

### Запуск генерации

`POST /vacancies/{vacancyId}/documents` — требует `Idempotency-Key`.

```json
{
  "kind": "COVER_LETTER",
  "sourceResumeId": "018f...",
  "instructions": "Сделай акцент на опыте с Docker"
}
```

`kind`: `RESUME` или `COVER_LETTER`. `instructions` — необязательное
пожелание пользователя, не более 1000 символов. Можно запросить оба типа
двумя отдельными запросами.

Ответ — `202` и операция (раздел 2.7). После `DONE` в `resultRef` лежит
документ.

Запрос отклоняется:

| Код | Причина |
|---|---|
| `404` | вакансия или резюме не найдены или чужие |
| `422` | резюме ещё не разобрано (`parseStatus` не `DONE`) |
| `429` | слишком много незавершённых операций |
| `503` | модель недоступна |

### Документ

```json
{
  "id": "018f...",
  "kind": "COVER_LETTER",
  "vacancyId": "018f...",
  "sourceResumeId": "018f...",
  "version": 2,
  "content": "Здравствуйте! ...",
  "origin": "AI",
  "createdAt": "2026-11-12T10:20:00Z"
}
```

### Версии

Документ **никогда не перезаписывается**. И перегенерация, и ручная правка
создают новую версию с `version + 1`. `GET /documents` по умолчанию отдаёт
последнюю версию каждого документа, `GET /documents/{id}/versions` — всю
историю. Предыдущую версию можно получить по `GET /documents/{id}?version=1`.

В БД `documentId` — постоянный ID строки `generated_documents`; тексты версий
лежат в `generated_document_versions` и связаны с ним через `document_id`.
`llm_request_id` хранится у версии, созданной моделью; при ручной правке
`origin = MANUAL`, а `llm_request_id` отсутствует.

`origin`: `AI` (сгенерировано) или `MANUAL` (правил человек). `PATCH` требует
`expectedVersion` в теле:

```json
{ "expectedVersion": 2, "content": "Исправленный текст" }
```

Если за это время появилась версия 3 — `409`, клиент перечитывает документ.

### Экспорт

`format=pdf` и `docx` формируются на бэкенде; `format=md` возвращает текст
последней версии в Markdown. Ответ — файл с `Content-Disposition: attachment`.
Экспорт синхронный и быстрый, так как модель не участвует.

## 10. База знаний

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/knowledge-items` | Список и поиск |
| `POST` | `/knowledge-items` | Добавить вручную |
| `GET` | `/knowledge-items/{itemId}` | Запись с ответом |
| `PATCH` | `/knowledge-items/{itemId}` | Изменить свою запись |
| `DELETE` | `/knowledge-items/{itemId}` | Удалить свою запись |
| `POST` | `/knowledge-items/generate` | Попросить нейросеть |

### Список

Фильтры: `q`, `kind` (`QUESTION` / `TASK`), `difficulty` (`JUNIOR` /
`MIDDLE` / `SENIOR`), `skillIds`, `origin` (`MANUAL` / `AI`), `authorId`,
`mine=true` — только свои.

В ресурсе записи поле `status` имеет значение `ACTIVE` или `ARCHIVED`.
Обычный список не включает архивные записи; вопросы, уже входящие в тесты,
остаются доступны через состав и результаты этих тестов.

В списке `answer` не возвращается — только заголовок, сложность и навыки. Так
пользователь может «подумать сам, потом подсмотреть» и список остаётся лёгким.

### Добавление вручную

```json
{
  "kind": "QUESTION",
  "title": "Чем отличается процесс от потока?",
  "body": null,
  "answer": "Процесс — ...",
  "difficulty": "JUNIOR",
  "skillIds": ["018f..."]
}
```

Ответ — `201`, запись с `origin = MANUAL`. Поле `origin` и `authorId` задаёт
сервер, клиент их не присылает.

### Генерация нейросетью

`POST /knowledge-items/generate` — требует `Idempotency-Key`.

```json
{
  "kind": "QUESTION",
  "skillIds": ["018f..."],
  "difficulty": "MIDDLE",
  "count": 5,
  "vacancyId": null,
  "instructions": "Вопросы из реальных собеседований"
}
```

`count` — от 1 до 10. Если указан `vacancyId`, модель получает контекст
вакансии и генерирует вопросы под неё. Ответ — `202` и операция. Записи
создаются сразу с `origin = AI` и ссылкой на запрос; `resultRef` указывает на
список созданных записей:

```json
{
  "type": "KNOWLEDGE_ITEMS",
  "ids": ["018f...", "018f..."],
  "href": "/api/v1/knowledge-items?operationId=018f..."
}
```

Для списка работает фильтр `operationId`, чтобы показать пользователю именно
то, что сгенерировано сейчас.

### Права на изменение

Редактировать и удалять запись может её автор. Администратор — любую. Записи,
которые входят в тест с попытками, не удаляются физически, а переводятся в
`status = ARCHIVED`; повторный `DELETE` на такую запись возвращает `409` с
пояснением. Если связанных попыток нет, запись удаляется физически. Статус
`ARCHIVED` в БД хранится как `archived`.

База знаний общая: читать записи могут все пользователи, в том числе чужие.

## 11. Тесты

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/tests` | Список тестов |
| `POST` | `/tests` | Создать вручную |
| `GET` | `/tests/{testId}` | Тест и состав |
| `PATCH` | `/tests/{testId}` | Изменить название и состав |
| `DELETE` | `/tests/{testId}` | Удалить свой тест; при наличии попыток — архивировать |
| `POST` | `/tests/generate` | Собрать нейросетью |
| `POST` | `/tests/{testId}/attempts` | Начать прохождение |
| `GET` | `/tests/{testId}/attempts` | Свои попытки по тесту |

### Создание вручную

```json
{
  "title": "Основы Python",
  "itemIds": ["018f...", "018f..."]
}
```

Порядок в массиве — порядок вопросов (`position`). Тест хранит **ссылки** на
записи базы знаний, а не копии: правка вопроса отразится во всех тестах.
При создании под вакансию её `vacancyId` сохраняется в `tests.vacancy_id`.
Если у теста нет попыток, `DELETE` удаляет тест и его связи `test_items`;
если попытки уже есть, тест переводится в `ARCHIVED`, чтобы сохранить историю.
Архивные тесты не показываются в обычном `GET /tests`, но доступны по прямому
ID для просмотра истории; начать новую попытку по архивному тесту нельзя (`409`).
Поле `status` в ресурсе теста возвращается как `ACTIVE` или `ARCHIVED`.

### Генерация

`POST /tests/generate` — требует `Idempotency-Key`.

```json
{
  "title": "Подготовка к вакансии",
  "skillIds": ["018f..."],
  "difficulty": "MIDDLE",
  "count": 10,
  "vacancyId": "018f..."
}
```

Ответ — `202` и операция; `resultRef` указывает на тест. Если подходящих
записей в базе знаний не хватает, недостающие создаются так же, как в
`/knowledge-items/generate`.

### Состав теста для прохождения

`GET /tests/{id}` отдаёт вопросы **без эталонных ответов**: только `id`,
`kind`, `title`, `body`, `position`. Эталон клиент получает только после
завершения попытки (раздел 11.2). Иначе его можно прочитать в DevTools до
ответа.

### 11.1 Попытки

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/attempts/{attemptId}` | Состояние попытки |
| `PUT` | `/attempts/{attemptId}/answers/{itemId}` | Сохранить ответ (автосохранение) |
| `POST` | `/attempts/{attemptId}/submit` | Завершить и проверить |
| `GET` | `/attempts/{attemptId}/result` | Результат и разбор |

`POST /tests/{id}/attempts` создаёт попытку и возвращает `201`:

```json
{
  "id": "018f...",
  "testId": "018f...",
  "status": "IN_PROGRESS",
  "startedAt": "2026-11-12T11:00:00Z",
  "answers": {}
}
```

Если у пользователя уже есть незавершённая попытка по этому тесту, возвращается
она же с `200`, а не создаётся новая. Так закрытая вкладка не плодит
«зависшие» попытки.

`PUT .../answers/{itemId}`:

```json
{ "userAnswer": "Процесс — это ..." }
```

Разрешено только пока попытка в `IN_PROGRESS`. После `submit` — `409`.
`itemId` должен входить в тест, иначе `404`.

### 11.2 Завершение и результат

`POST /attempts/{id}/submit` идемпотентен: для уже завершённой попытки
возвращает текущее состояние, а не запускает проверку повторно.

Ответы на вопросы с развёрнутым ответом и задачи проверяет модель — это
операция. Поэтому `submit` возвращает:

- `200` и `status = COMPLETED`, если проверять было нечего или всё посчиталось
  сразу;
- `202` и `status = CHECKING` с `operationId`, если идёт проверка моделью.

При `CHECKING` ID операции — это ID связанной строки `llm_requests`. Если
проверка завершается ошибкой или её отменяют, операция получает `FAILED` или
`CANCELLED`, а попытка возвращается в `IN_PROGRESS`, чтобы пользователь мог
отправить её на проверку ещё раз.

`GET /attempts/{id}/result` отвечает `202`, пока попытка в `CHECKING`.
После `COMPLETED`:

```json
{
  "attemptId": "018f...",
  "status": "COMPLETED",
  "score": 72,
  "finishedAt": "2026-11-12T11:20:00Z",
  "answers": [
    {
      "itemId": "018f...",
      "title": "Чем отличается процесс от потока?",
      "userAnswer": "...",
      "isCorrect": true,
      "feedback": "Верно, но стоит упомянуть общую память",
      "referenceAnswer": "Процесс — ..."
    }
  ],
  "weakSkills": [{ "id": "018f...", "name": "Docker", "correctRate": 0.3 }]
}
```

`weakSkills` считается по `item_skills` неверных ответов. Если попытка
сделана в контексте вакансии, фронтенд может сопоставить эти навыки с
`/vacancies/{id}/match` и показать пробелы.

`score`, `isCorrect` и `feedback` из тела клиентских запросов **не
принимаются**.

## 14. Рекомендации для React-клиента

Это не часть контракта, а то, что из него следует.

- **Состояние сервера** держите в TanStack Query (или RTK Query): кеш,
  повторные запросы, polling операций через `refetchInterval` уже есть.
- **Старт приложения:** `GET /auth/csrf` + `GET /auth/me`. `401` → экран
  входа, остальные запросы не отправляются.
- **Операции:** один общий хук `useOperation(id)` с polling раз в 2–3 с,
  остановка на `DONE`, `FAILED`, `CANCELLED`. Все генерации (документы,
  записи, тесты) используют его.
- **Кнопки генерации:** блокировать на время операции и всегда отправлять
  `Idempotency-Key`, сгенерированный **при открытии формы**, а не при клике —
  тогда двойной клик и повтор после обрыва сети не создадут дубль.
- **Загрузка резюме:** прогресс файла из `XMLHttpRequest`/`axios`, затем
  polling `parseStatus`.
- **Автосохранение ответов теста:** `PUT` с debounce около 1 с, индикатор
  «сохранено».
- **Ошибки:** общий обработчик по `application/problem+json`, `errors[].field`
  привязывать к полям формы.
- **Типы:** не писать вручную, а генерировать из `openapi.yaml`.

## 15. Что API сознательно не делает

| Нет | Почему |
|---|---|
| `POST /vacancies`, `PATCH /vacancies/{id}` | Вакансии принадлежит парсер, ручное редактирование расходится с источником и затирается следующим парсингом |
| `DELETE /vacancies/{id}` | Вакансии архивируются, на них ссылаются документы |
| `POST /skills` | Справочник пополняется только нормализацией, иначе появятся дубли «Postgres» и «PostgreSQL» |
| выдача эталонных ответов до завершения попытки | Их можно прочитать в DevTools |
| приём `score`, `isCorrect` от клиента | Всё считает бэкенд |
| `PUT /documents/{id}` с заменой версии | Версии неизменяемы, правка создаёт новую |
| выдача `raw_text` резюме и промптов обычному пользователю | Лишние персональные данные |
| отправка отклика на вакансию | Вне объёма V1, Jobly готовит документы, но не подаёт заявки |
| WebSocket | Хватает polling и необязательного SSE, меньше требований к бэкенду |
